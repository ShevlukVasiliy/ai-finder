Ты ведёшь проект AI-Finder от пустой папки до задеплоенного и протестированного продукта. Работай автономно, этап за этапом, и не останавливайся, пока не выполнишь критерии готовности (см. конец). Вопросы задавай только если упёрся в то, что можно получить лишь от меня: секреты, доступы, ID облака. Всё остальное решай сам и фиксируй решения в `docs/DECISIONS.md`.

## Источник требований

Полное ТЗ лежит в `TZ.md` в корне репозитория. Прочитай его целиком перед началом: это главный источник истины. Ключевые ограничения из него:
- Только эвристики и классическая статистика. **Никаких LLM и внешних AI API** — ни для анализа, ни для советов.
- Сервис не переписывает контент, а только подсвечивает проблемы и даёт советы. Исключение — явная очистка символов (T-01/T-02) по кнопке.
- Языки RU и EN. Контент: текст, документы (DOCX/PDF/TXT/MD/ODT/RTF), изображения, код.

## Стек

- **Только фронтенд, без бэкенда:** React + TypeScript + Vite, Tiptap для редактора с подсветкой, Vitest + Testing Library + fast-check, Playwright для e2e. Весь анализ выполняется в браузере.
- **Монорепо:** `frontend/`, `rules/` (YAML со словарями, порогами и советами), `.github/workflows/`, `docs/`.

## Тесты — обязательны на каждое действие

Правило: **ни одна фича не считается сделанной без тестов. Пиши тест до или вместе с кодом.**

- **Каждый детектор:** юнит-тесты с фикстурами «человек / ИИ / пограничный случай» для RU и EN, а также тест на пустой и короткий ввод. Property-based тесты (fast-check): детектор не падает на произвольном unicode, score всегда в [0, 1].
- **Движок советов:** находка → правильное правило; подстановки; приоритизация по `expected_gain`; объединение связанных находок; валидация всех YAML-правил по схеме (отдельный тест, который падает при битом правиле).
- **Парсеры документов и изображений:** тест на каждый формат с реальными файлами-фикстурами в `frontend/tests/fixtures/`. Фикстуры генерируй сам скриптом `scripts/make_fixtures.*`, включая docx, PNG с чанком `parameters` и т. д.
- **Пайплайн анализа:** тест публичных функций (`analyze`, `recheck`, `normalize`, `rules`) — успех, ошибки валидации, лимиты размера, неподдерживаемый формат.
- **Frontend:** юнит-тест на каждый компонент и хук; на каждое действие пользователя (вставка текста, загрузка файла, drag-n-drop, перепроверка, применение очистки, фильтр советов, экспорт, смена темы) — тест с Testing Library.
- **E2E (Playwright):** полный сценарий для каждого типа контента: загрузил → отчёт → поправил → перепроверил → score изменился. E2E идёт против собранной статики (`vite preview`).
- **Регрессия качества:** `frontend/tests/quality/` с мини-корпусом размеченных текстов. Тест проверяет ROC-AUC ≥ 0,8 и FPR на человеческих текстах ≤ 10 % на этом корпусе.
- **Покрытие:** ядро анализа ≥ 85 %, UI ≥ 80 %. Порог зашит в CI, и при недоборе CI падает.

## Деплой

- Статика публикуется в **GitHub Pages** (`/ai-finder/`, SPA fallback через `404.html`).
- GitHub Actions в `.github/workflows/`:
  1. `ci.yml` — на каждый PR и push: lint, typecheck, юнит-тесты и покрытие с порогами, e2e Playwright.
  2. `deploy.yml` — после зелёного CI на `main`: сборка, публикация в Pages, **smoke-тест** по публичному URL.
- Описание — в `docs/DEPLOY.md`.

## Порядок работы

Иди по этапам из раздела 13 ТЗ. На каждом этапе:
1. Короткий план в `docs/PROGRESS.md`.
2. Тесты → реализация → прогон всех тестов локально.
3. Коммит с понятным сообщением (conventional commits). Один этап — одна или несколько логичных веток/PR.
4. Отметка в `docs/PROGRESS.md`: что сделано, что отложено и почему.

Начни с каркаса: монорепо, линтеры, пустые CI и deploy-пайплайны. Деплой «hello world» должен заработать раньше бизнес-логики, чтобы дальше каждый этап сразу выкатывался.

Если тест падает — чини код, а не тест. Тест разрешено менять, только если он объективно неверен; причину зафиксируй в коммите. Не помечай задачу выполненной, пока тесты не зелёные.

## Критерии готовности («до талого»)

- [ ] `README.md` (запуск локально одной командой `pnpm dev`), `docs/DEPLOY.md`, `docs/DECISIONS.md`, `docs/PROGRESS.md` актуальны.
- [ ] Регрессия качества на корпусе проходит пороги.

Когда всё готово, дай итоговый отчёт: URL прода, метрики качества, покрытие, список отложенного.
